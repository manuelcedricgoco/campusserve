## 3. AI foundation (proposed)

Principles: provider-independent; keys never in the database or frontend; retrieval filtered by the
caller's permissions inside the database; AI tables have **no write path into official records**.

| Table | Key columns (abridged) | Notes |
|---|---|---|
| `ai_provider_settings` | `provider` (`mock`, later e.g. `openai`, `anthropic`, `gemini`, `ollama`), `purpose` (`chat`/`embedding`/`classification`), `model`, `embedding_dimensions`, `is_enabled`, limits (`max_requests_per_user_per_day`, `max_tokens_per_request`, `timeout_ms`), `secret_ref` (the **name** of a backend env var or Vault secret — never the key) | Only `mock` seeded. No paid provider assumed |
| `ai_prompt_templates` | `code`, `version`, `purpose`, `body`, `is_active`, `created_by` | Versioned; one active version per code; seeded with guard-rail system prompts (no university policy text) |
| `ai_knowledge_sources` | `name`, `source_type` (`official_policy`, `office_guide`, `faq`, `general`), `is_official`, `owner_office_id` / `owner_organization_id`, `visibility` (`public`, `authenticated`, `permission`), `required_permission`, `status` | `is_official` lets answers distinguish official documents from general information |
| `ai_knowledge_documents` | `source_id`, `title`, `version`, `supersedes_id`, `storage_path` (new private bucket `ai-knowledge`), `mime_type`, `size_bytes`, `checksum_sha256`, `processing_status` (`uploaded → extracting → chunking → embedding → ready` / `failed`), `effective_from`, `is_current` | One current version per document lineage; old versions kept |
| `ai_document_chunks` | `document_id`, `chunk_index`, `content`, `token_count`, `page_from/to`, `search_tsv` (generated `tsvector`) | GIN index on `search_tsv`; trigram index for fuzzy match |
| `ai_embeddings` | `chunk_id`, `provider_setting_id`, `model`, `dimensions`, `embedding vector` | See decision D3 on dimensions; HNSW (cosine) index per approved model |
| `ai_conversations` | `user_id` (null for public), `channel` (`authenticated`, `public`), `public_session_hash`, `title`, `status`, `expires_at` | Public sessions are anonymous, short-lived, rate-limited by the backend |
| `ai_messages` | `conversation_id`, `role` (`user`/`assistant`/`system`/`tool`), `content`, `citations jsonb` (chunk/document ids), `provider`, `model`, `prompt_template_id`, `input_tokens`, `output_tokens`, `latency_ms`, `error_code` | Assistant answers keep the exact sources used |
| `ai_feedback` | `message_id`, `user_id`, `rating` (−1/1 or 1–5), `reason`, `comment` | One per user per message |
| `ai_processing_logs` | `document_id`, `stage`, `status`, `duration_ms`, `error_message` | Document pipeline failures |
| `ai_usage_logs` | `user_id`, `feature` (`assistant`, `search`, `classification`, `summarization`, `analytics`, `queue_insights`, `admin_assistant`), `provider`, `model`, tokens, `latency_ms`, `status`, `error_code` | No message content, so it can be shown to admins |

Functions (proposed):
- `private.can_access_knowledge_source(source_id)` — public / authenticated / permission rules for `auth.uid()`.
- `public.search_knowledge(query_embedding, model, match_count, min_similarity, include_fulltext_query)` —
  **hybrid** retrieval (vector + full-text), only over current, `ready` documents the caller may access;
  returns chunk text, document title/version, `is_official`, similarity.
- `public.search_knowledge_text(query, match_count)` — full-text/trigram only (works with no AI provider).
- Public assistant: the backend calls retrieval restricted to `visibility = 'public'` sources.

AI decision boundary (enforced structurally, not only by prompt):
1. The AI module runs with the **signed-in user's own JWT**, so it can never see or do more than that user.
2. In Phase 2 the AI module is given **read-only tools only**; it cannot call approval/verification/penalty
   functions. AI request classification only writes a *suggested* category to a separate column/table; a
   human makes every official decision.
3. No AI table has a foreign key or trigger that changes clearance, receipt, violation, penalty or payment state.

## 4. Advanced GIS foundation (proposed)

Storage: `geometry(<type>, 4326)` (EPSG:4326, lon/lat), GiST index on every geometry column; distances and
lengths computed as `geography` in metres. GeoJSON in/out via `ST_GeomFromGeoJSON` / `ST_AsGeoJSON`.
Validation: `ST_IsValid`, correct geometry type, SRID 4326, coordinates inside a coarse Philippines bounding
box (generic sanity check, not campus data), and — once the campus boundary is **verified** — inside it.

| Table | Geometry | Purpose |
|---|---|---|
| `campuses` | `boundary` MultiPolygon (nullable), `reference_point` Point (nullable) | Seeded with **one row: OMSU Mamburao Campus, no geometry, `verification_status = 'unverified'`** |
| `location_categories` | — | Building, office, service counter, gate, landmark, parking, restroom, ... (lookup) |
| `gis_data_sources` | — | Provenance: `administrator_entry`, `field_survey`, `openstreetmap` (license ODbL + attribution text), `university_records`, `import` |
| `campus_map_layers` | — | Layer name, `layer_type`, style JSON, `visibility` (`public`, `authenticated`, `restricted`), `required_permission`, order |
| `campus_buildings` | — | Building identity (name, code, floors, campus, owner department) |
| `campus_building_boundaries` | Polygon/MultiPolygon | **Versioned** footprints; one current per building; verification status; source |
| `campus_locations` | Point | Points of interest (entrances, rooms, counters, landmarks); optional `building_id`, `floor`, `owner_organization_id`, `owner_department_id`; layer; verification status |
| `office_locations` | — (links) | `office_id` ↔ `campus_location_id`, `is_primary` (one primary per office) |
| `service_locations` | — (links) | `service_id` ↔ `campus_location_id`, `is_primary` — connects queue/services to the map |
| `campus_paths` | LineString | Walking path segments with `length_m`, `source_node`/`target_node`, `is_accessible`, `surface`, `is_one_way`, verification status. **Routing uses only verified segments** |
| ➕ `campus_path_nodes` | Point | Routing graph vertices (pgRouting needs integer node ids); built by a function from verified path endpoints. *Additional table, needed for pgRouting* |
| `location_accessibility` | — | Accessibility features for a location or path (ramp, elevator, stairs, wheelchair-accessible restroom, ...) |
| `gis_location_verifications` | — | Append-only verification history for buildings, boundaries, locations, paths: who, when, decision, method, evidence, previous/new geometry |

Every spatial feature carries `verification_status` (`unverified`, `pending_review`, `verified`, `rejected`,
`retired`), `data_source_id`, `layer_id` and `visibility`. Verification is a separate step from editing
(the editor cannot verify their own edit — four-eyes rule, enforced by CHECK + function).

Functions (proposed):
- `public.register_campus_location / update_campus_location` (geometry validated, history kept),
  `public.verify_gis_feature(type, id, decision, notes)`, `public.import_gis_geojson(...)` (staging +
  validation report; imported features start `unverified`).
- `public.map_features(layer_ids, bbox)` → GeoJSON FeatureCollection filtered by visibility.
- `public.search_campus_locations(query)` → trigram + full-text search over names, offices, services.
- `public.find_walking_route(from_location, to_location, alternatives, accessible_only)` → pgRouting over
  verified paths; returns `{status: 'unavailable', reason}` when the graph is empty or disconnected — **never
  an invented route**.
- `public.nearest_service_locations(point, service_id, limit)`.
- Analytics: `public.gis_activity_by_location(from, to, metric)` aggregating existing `queue_tickets`,
  `service_requests`, `receipt_records`, `penalty_payments` through `office_locations` / `service_locations`
  (heatmap and distribution data; counts only, no personal data).

**Seeded geographic data: none except the unverified campus row, categories, layers (empty) and data
sources.** No building, boundary, coordinate or path is seeded. Administrators register and verify them.

## 5. Automation foundation (proposed)

Execution model (recommended — decision D4): **database-side event capture + table-based outbox**.
1. Lightweight triggers on existing tables insert a row into `automation_events` (event type, entity, payload,
   `idempotency_key`); duplicates are ignored (`ON CONFLICT DO NOTHING`).
2. A matcher creates `automation_executions` for enabled rules whose trigger and conditions match.
3. Executions are claimed with `FOR UPDATE SKIP LOCKED`, run, retried with backoff up to `max_attempts`,
   then marked `dead` and written to `automation_error_logs`.
4. In-database actions (in-app notification, reminder, clearance re-evaluation) run in SQL; external actions
   (email/SMS, report generation) run in the backend worker (Phase 2) that claims the same rows.
5. `pg_cron` runs the scheduler (`scheduled_jobs`) and the in-database executor every minute.

| Table | Purpose |
|---|---|
| `automation_triggers` | **System catalog** of supported events (e.g. `service_request.submitted`, `service_request.status_changed`, `queue_ticket.status_changed`, `receipt.verified`, `clearance.step_approved`, `clearance.requirement_changed`, `payment.status_changed`, `community_service.verified`, `violation.verified`, `schedule.tick`) with payload schema |
| `automation_rules` | Admin-configured rules: trigger, `conditions jsonb` (validated operators only), scope (`organization_id`/`office_id`, optional), enabled, version |
| `automation_actions` | Ordered actions of a rule; `action_type` from a **whitelist**: `send_notification`, `send_reminder`, `escalate_to_position` (notify only), `reevaluate_clearance`, `generate_report`, `record_note`. There is **no** approve / verify / reject / assess / pay action type — enforced by a CHECK constraint |
| ➕ `automation_events` | Event outbox with unique `idempotency_key`. *Additional table, needed for idempotency and replay* |
| `automation_executions` | One per (rule, event): status `queued/running/succeeded/failed/dead/skipped`, attempts, `next_attempt_at`, lock info, unique `(rule_id, event_id)` |
| `automation_execution_logs` | Step-by-step log of an execution |
| `automation_error_logs` | Failures, including scheduler and trigger errors |
| `scheduled_jobs` | Named jobs: cron expression, `job_type` whitelist (`pending_request_reminders`, `overdue_request_escalation`, `clearance_deadline_reminders`, `generate_queue_slots`, `scheduled_report`, `expire_public_ai_sessions`), enabled, last/next run, last status |
| `notification_templates` | Code, channel (`in_app` now; `email`/`sms` only when a provider is configured), subject/body with named placeholders, version, active |
| `notification_delivery_logs` | Per notification per channel: status, attempts, provider message id, error |

Existing behavior is kept: workflow functions keep writing their current notifications (tested). Automation
**adds** reminders, escalations and re-evaluation; it does not duplicate existing notifications.

Deadlines: no deadline fields exist today, so "approaching deadline" and "overdue" need new nullable fields
(§6). Their values (processing days per service, clearance deadlines) are **not confirmed** and are left
null until offices configure them; jobs skip records without a deadline.

`pgmq` was evaluated and not proposed: the outbox table gives idempotency, audit and visibility in one place
without another moving part. It can be adopted later without schema conflict.

## 7. Security and governance

- RLS enabled on every new table; same model as today: `SELECT` via policies, writes via checked
  `SECURITY DEFINER` functions or the backend service role. `anon` stays without table access (decision D2).
- AI conversations/messages/feedback: owner only. Admins see `ai_usage_logs` (no content), not conversations
  (decision D5).
- Knowledge sources/documents/chunks/embeddings: readable only through `can_access_knowledge_source`;
  managing requires `ai.manage_knowledge`.
- Provider secrets: backend environment variables (or Supabase Vault, read by the backend only).
  `ai_provider_settings.secret_ref` stores a name; a CHECK rejects values that look like keys.
- Automation configuration: `automation.manage` (admin); monitoring: `automation.view` within scope.
  Action whitelist excludes every official decision. Executor functions are service-role / cron only.
- GIS: per-layer and per-feature visibility; restricted features require `gis.view_restricted`;
  editing and verification separated; full verification history; geometry validation in the database.
- Payments: unchanged — webhook idempotency already in place; automation only *reacts* to
  `payment.status_changed` (notifications, re-evaluation), never sets payment state.
- All new functions: `SET search_path = ''`, qualified names, explicit `GRANT EXECUTE`.

1. Local: install PostGIS/pgvector/pgRouting/pg_cron, build from scratch, run **all 161 existing checks**
   (regression) plus new suites: `070_ai`, `080_gis`, `090_automation`, `100_extension_rls`.

3. Compare schema fingerprints local ↔ live; re-run every suite on live (rolled back).
4. Confirm existing data counts unchanged (profiles 18, students 10, slots 960, audit rows only grow).
5. Run security and performance advisors; record findings.
6. Update `DATABASE_SCHEMA.md` (+ERDs), `DATABASE_TABLE_REFERENCE.md` (regenerated),

Size/plan impact (Free plan, 500 MB): AI embeddings at 1 536 dims ≈ 6 KB per chunk (10 000 chunks ≈ 60 MB);
at 768 dims ≈ 3 KB. GIS data for one campus is negligible.
